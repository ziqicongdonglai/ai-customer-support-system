# AI 辅助开发实践

在本项目的开发过程中，AI 主要用于代码检索、方案分析、局部实现和验证辅助。AI 生成的代码不会直接成为最终结果：修改前先检查现有实现和影响范围，修改后通过测试、构建、运行验证与 diff review 确认行为是否正确，再由开发者决定是否接受。

这套实践关注的不是一次生成更多代码，而是让每次修改保持可理解、可检查和可验证。遇到异常时，也会先判断问题属于代码、配置、依赖还是运行环境，再决定是否需要修改实现。

## 开发流程

```text
明确问题和修改范围
→ 阅读现有实现与相关约束
→ AI 辅助完成小范围修改
→ 执行 tests / lint / build / runtime verification
→ Review diff 和运行结果
→ 接受、修正或停止
```

AI 适合承担仓库检索、重复实现、跨文件修改、验证辅助和结果汇总。需求判断、架构选择、范围控制、正确性判断与最终验收仍由开发者负责。AI 可以提出后续建议，但建议不会自动变成新的开发工作。

## 风险控制

1. **先阅读现有实现，再修改。** 确认责任层、既有接口和可复用工具，避免根据模型记忆猜测项目结构。
2. **修改前明确范围和验收标准。** 说明本次解决什么、不解决什么、如何验证，以及达到什么条件后停止，避免局部需求演变成无关重构。
3. **架构变化需要确认。** 如果实现涉及新依赖、跨层通信、公共接口或职责迁移，不作为普通代码修改直接完成，而是先确认方案和影响范围。
4. **用测试和运行结果证明修改有效。** 根据仓库实际能力执行 tests、lint、build 和 runtime verification；“看起来正确”不能替代可重复的结果。
5. **Review diff，而不只看最终页面。** 检查无关改动、遗漏的集成点、异常处理、隐式行为变化和意外依赖。
6. **生成结果必须经过 Review。** 结合代码、diff、遗漏的集成点、异常处理和运行结果进行检查，验证通过后才接受修改。

自动化检查可以验证已经覆盖的行为，但范围、架构和跨模块正确性仍需要工程 Review。

## 工程案例

### 先定位故障层，而不是看到报错就改代码

一次 DeepSeek streaming 在选择 Tool 前遇到 SSL certificate-chain failure。排查首先聚焦环境和 TLS 链路，而不是立即修改 Provider 或业务代码，也没有通过关闭证书验证、使用 `verify=False` 或更换模型来绕过错误。

调整本地运行环境后，TLS、认证请求和 streaming verification 均通过，原有业务链恢复正常。该 blocker 不需要任何 application-code change。

这个案例说明，环境或配置问题不应被误修成产品代码问题，更不能为了让错误消失而降低安全检查。可靠的修复从定位故障层开始。

### AI 生成代码不等于集成完成

在 Tool Calling 集成中，AI 辅助完成了 Provider streaming、Tool execution、业务查询、第二次模型调用和结果持久化。自动验证和实际调用已经能够通过，但在跨模块 Review 中发现：新增的 Tool instruction 是在上下文预算完成后追加的，因此绕过了原有 message token budget。

修正复用了现有 ContextBuilder，通过 `system_suffix` 在分配 RAG 和历史消息预算前统一计算 instruction。随后增加定向回归验证，确认 instruction 会占用预算，知识片段和历史消息不会继续使用已被占用的空间，同时保留普通 streaming 与 Tool Calling 行为。

该案例说明，自动化测试只能证明已覆盖的行为。跨模块契约、隐藏成本和集成约束仍需要通过代码 Review 识别，生成完成不等于工程集成完成。

## 实践原则

AI 扩展了代码检索、方案分析和实现能力，但不能替代工程判断。生成代码需要能够被理解、验证和解释；需求、架构、范围与最终验收仍由开发者负责。

实践重点不是追求一次生成多少代码，而是保证修改范围清晰、结果可验证。当证据指向环境或配置而不是应用实现时，不应仅为了消除错误而修改产品代码。
